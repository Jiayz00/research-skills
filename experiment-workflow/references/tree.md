# 实验树：形状、轮次与停止

## 节点与状态

- 每个节点 = 一条普通 Git 分支 = 一次尝试。根节点是 baseline（基线）。
- 默认分支名 `exp/<slug>`；仓库已有分支命名 convention 时优先沿用。
- 节点有两种状态：
  - **provisional（临时）**：运行还没有回答它的问题。可以就地改代码、修依赖、重跑。
  - **frozen（冻结）**：运行回答了它——拿到结果，好、坏、nan 都算。分支永久不得再改；新假设从它拉 child。
- **未预期的行为不算回答**：OOM、超时、由 bug 造成的发散、缺依赖——这些是工程/硬件问题，节点仍是 provisional（除非该节点的假设本身就是关于内存或运行时，那这个结果正是它要的）。
- **修复上限**：同一节点连续两次运行什么都没答上，停下来问用户；同一个失败在第二个节点上再次出现，是一个 setup 问题，立即问用户。裸重跑、换设备或换后端都算一次修复。
- **工程失败 vs 科学结果**：工程失败不进入最终均值；科学结果（包括失败/退步）保留并交给 `experiment-analysis` 解释。

## 树形：stacked bushes，不是 flat fan，也不是 noodle

```text
FLAT FAN（错）               NOODLE（错）            STACKED BUSHES（对）
root                         root                    root
├ a ├ b ├ c ... ├ n          └ a                     └ lr-head       ┐ 第 1 轮：
                               └ b                      ├ lr 2e-5    │ 同一决策的
                                 └ c                    └ lr 3e-5    ┘ 小扇形
                                   └ d ...                └ winner ── arch-head  ┐ 第 2 轮
                                                             ├ arch-A              │ 叠在胜者上
                                                             └ arch-B              ┘
```

- **Flat fan**：所有选项挂在根上——每个结果都在和起点比，胜势永远不累积。
- **Noodle**：长单链——每一步并没有真建立在上一节点之上，深度是硬凑的。
- **Stacked bushes**：一轮内小扇形（一个决策的并列选项），取胜者，下一轮从胜者继续下钻。

**唯一决定形状的规则**：在把 X 建成 Y 的子节点之前，说出 Y 确立了、而 X 建立在其上的东西。

- **说得出来**（“Y 是学习率胜者；X 保留这个学习率、改结构”）→ X 是 Y 的 child，下钻。
- **说不出来**（X 和 Y 是同时尝试的并列选项：lr 2e-5 vs lr 3e-5）→ 它们是同一丛的 sibling，扇形展开，不要串成链。

所以：**宽 = 一个决策尚未收敛的选项**（一轮内的 3 路学习率对比就该是同一个父节点下的三个兄弟）；**深 = 已解决的决策、逐层叠加**（每保住一个胜者就下移一层）。新一轮永远挂在上一轮胜者上，而不是根上。

每轮开始时重读一次树（`git log --all --graph --oneline`，或仓库自己的实验台账），检查形状：

- 根下面一大排子节点、没有孙节点 → 该下钻却一直在扇形；
- 一条深度 N 的单链、没有分叉 → 把该并列的兄弟串成了链。

## 轮次与父节点

一轮 = 一个决策的全部并列选项，挂在同一父节点下。

- 第 1 轮：父节点 = 基线（还没有任何胜利者）。
- 之后每一轮：父节点 = 上一轮确认的胜者——本轮改动叠在上一次增益之上，而不是回到起点。
- 需要外部方法/新假设时，先让 `optimization-advisor` 给出排序方案，再把其中一个方案变成新 child；一次只测一个变量。

每个待跑的选项，在它的分支/提交说明里写清两件事：**具体改动**、**它要测量的东西**。说不清要测什么的节点不要建。

## 停止

- 目标达成，或连续约 3 次失败/回退 → 停。
- 停止时把树写成一份可读的实验总结（放入产出目录，见 `evidence.md`）。
- 任何跑过或改过实验的回合，都用一段简短总结收尾：每个相关节点一行——测了什么、状态、头条结果。纯问答、没动实验的回合不用总结。
- 总结里的数字必须来自 `experiment-analysis` 核验过的日志/指标；不要把未验证的 advisor proposal 写成实验结论。

## 日志与笔记（notes）

在分支上留下笔记，给未来的自己和其他会话读：

- 首选仓库已有的记录约定；没有约定时，用 `notes/<branch>.md` 或提交信息本身。
- 记录观察、假设、进行中的总结；每轮结束或拿到重要结果时更新。
- 更新是整篇覆盖式时，先读、再改、再写回，避免丢旧内容。
- run manifest 字段见 `runs.md`；分析和方案分别交给 `experiment-analysis`、`optimization-advisor`。
